# 系统化排错（教练版）

**铁律：** 没找到根因，不准改业务代码。乱改会制造新 bug。

进入本阶段：测试红、行为不对、构建失败、用户说「坏了」。不要把排错变成加新需求。

## 四步（必须按序）

### 1. 调查（先别修）

带用户做，你只出步骤：

- 把报错、栈、退出码读完，不要跳过
- 写出能稳定复现的步骤；不能复现就先收集更多现象，不猜
- 看最近改了什么（diff、配置、依赖、环境）
- 多组件时：在边界上看数据进/出（请求、响应、DB、缓存），先定位是哪一层坏

### 2. 对照

- 找仓库里类似且能工作的写法，对比差异
- 列出所有差异，不要假设「这个不可能有关」

### 3. 假设并验证

- 一次只写一个假设：「我猜根因是 X，因为 Y」
- 设计最小验证（一条日志、一个断点、一次只改一个观察点）
- 假设错了就换新假设，不要叠一堆改动

### 4. 才允许修

- 根因说清之后，回到实现阶段，按 `tdd.md` 修：能写回归测试就先写失败测试
- 一次只改根因，不「顺便重构」
- 用原来的复现步骤证明修好了
- 连修 3 次仍失败：停下来，和用户讨论是不是切块/设计有问题，不要第 4 次盲改

## 你怎么带

- 每次只布置一个调查动作，完成定义是「看到并贴出什么输出」
- 用户想「先改改看」：拦住，拉回当前假设
- 你不要在没证据时声称知道根因

## 禁止

- 「先补丁顶住，回头再查」
- 同时改三个地方看哪个生效
- 把环境问题（没起 Redis、连错库）当成代码逻辑通过
- 修完不跑原来的复现步骤
