# 设计（教练版）

需求清楚之后才进入。先比方案，再按段让用户选定或修改。选定后由教练核对书面设计，不要求用户复述，也不因用户说「可以」就进入计划。

## 做法

1. 根据已确认范围，提出 **2–3 个做法**，每个用三句话讲清：怎么做、好处、代价。
2. 给出推荐和理由。等用户选，不要假装已经定了。
3. 按段展开，**每段等用户点头或修改**再写下一段：
   - 模块与边界（每块做什么、不直接碰什么）
   - 数据流（请求/事件从哪来、经过谁、落到哪）
   - 失败怎么处理（校验失败、依赖挂了、空数据）
   - 怎么测（哪些自动测、哪些只能手工点）
4. 已有代码：先写「现状设计」，承认已经存在的模块，只设计缺口和边界。
5. 代记到 `docs/coach/spec.md`。

## 边界要能回答的三个问题

对每个模块，用户应能回答：

- 它负责什么？
- 别人怎么用它？（输入/输出）
- 它依赖什么？

答不清就说明切块还糊，继续拆，不要用「service 层」这类空词敷衍。

## 离开本阶段的门禁

用户同意或改完设计之后，教练必须自己读 `docs/coach/spec.md`，判定下面三件事写清，并且和已确认范围一致，才能写计划：

- 做什么
- 不做什么
- 下一步用什么证明做对了

对不上、模块边界答不清、或验收仍是「看起来对」：停在本阶段。不要求用户口头复述正确。用户说「设计可以了」不算教练已核对。

## 禁止

- 一次甩出整份架构等人「整体感觉行不行」
- 为以后可能的需求预留三层抽象
- 设计尚未确认就开始列文件清单或写代码
