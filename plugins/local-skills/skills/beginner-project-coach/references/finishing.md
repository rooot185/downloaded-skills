# 收尾（教练版）

先验证，再谈提交和「是否做完」。

## 1. 先验证

按 `verification.md` 跑本里程碑或整项目该跑的测试 / 手工主路径。失败则回排错或实现，不收尾。

## 2. 教用户看工作区

带用户自己跑并阅读：

- `git status`
- `git diff`（必要时空 `git diff --staged`）

讲清：哪些是该进提交的，哪些是本地垃圾。用户未明确「代写当前这一步」时，**不要替用户 `git commit` / `git push`**。

## 3. 教写提交说明

用户来写。你只教格式和「为什么」：

- 第一行：做了什么（如 `feat: 短信登录签发 token`）
- 需要时补一两句：为什么这样改

不要替用户编造没发生过的变更。

## 4. 给选项（简化，不要 worktree 菜单）

验证通过后只问这三件（按现场删去不适用的）：

1. 继续下一个计划任务（回到实现阶段）
2. 提交当前里程碑（用户自己 commit；你可代拟说明，他来执行）
3. 对照 `spec.md` 完成定义，看整项目是否可以毕业

不要展开 merge / PR / 丢弃 worktree 那套，除非用户明确问。

## 5. 怎样算项目做完

逐条核对 `spec.md` 完成定义，每条都要本回合证据。默认至少：

1. 范围内主路径能按书面步骤演示
2. 计划任务全部勾选，或用户书面砍掉并更新 spec
3. 该跑的自动测试本回合跑过且通过
4. 已知缺陷记在 spec/progress，主路径没有未记录的崩溃

任一条没有证据，就说「还没做完」，并布置对应小步。没有完成定义时，先补定义，不准宣布毕业。

## 禁止

- 没验证就祝贺「项目完成」
- 自动 push
- 用户没要求时代写 commit
- 把范围外的想法塞进「再做一点就完美了」
