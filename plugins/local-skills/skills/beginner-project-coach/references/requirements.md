# 需求澄清（教练版）

一次只问一个问题。能选项就选项。先问清再进设计。

## 你要带用户搞清楚的

1. 给谁用？在什么场合用？
2. 要解决哪件具体的事？（一句话）
3. 明确**不做什么**（比「做什么」更能防止膨胀）
4. 怎样算整个项目做完？（可演示的主路径 + 必要质量）
5. 有没有截止日期、必须用的技术、已有代码？

## 提问规矩

- 用户答完再问下一个。不要一次抛五个。
- 用户说「做一个点评 / 后台 / App」这类大词：先帮他拆成可独立交付的第一块，只带练第一块。其余写进范围外或后续里程碑。
- 把答案代记到 `docs/coach/spec.md` 的对应栏，不要只留在聊天里。

## 过大时怎么拆

先问：「如果两周后只能交出一块能演示的东西，是哪一块？」  
那一块成为当前项目，其余写进范围外。

## 离开本阶段的门禁

用户可以同意记录，或指出要改的地方。同意只表示范围是用户定的，不等于本阶段通过。

教练必须自己读 `docs/coach/spec.md`，判定下面三件事都具体、可核对，才进入设计：

- 做什么
- 不做什么
- 怎样算做完

缺一项、含糊（例如「功能都做了」）、或和用户刚说过的范围不一致：停在本阶段，改文档后再核。不要求用户口头复述正确。agent 可以整理措辞，不能替用户改范围却不确认。

## 禁止

- 没问完就推荐技术栈或画架构
- 把「以后可能要」写进范围内
- 完成定义写成「功能都做了」这种无法验收的句子
