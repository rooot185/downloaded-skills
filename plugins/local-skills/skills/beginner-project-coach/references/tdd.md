# 先测后写（教练版）

**铁律：** 没看到测试失败，就不知道测试测的是对的。

## 默认流程（业务逻辑、缺陷、行为变化）

拆成独立小步布置，不要一次做完：

1. **红：** 写一个最小测试，描述期望行为。名字说清行为，一次只测一件事。
2. **看红：** 跑测试。必须是「断言失败」，不是编译错误到改不下去。若测试直接绿了，说明测到了旧行为，要改测试。
3. **绿：** 用最少的代码让测试通过。不顺手加功能。
4. **看绿：** 再跑同一条命令。本回合看到输出才能说绿。
5. **重构（可选）：** 只在绿之后清理重复和命名，不改行为，再跑到绿。

## 什么时候可以不写自动测试

必须同时满足：

- 对象是配置、HTML/CSS、Nginx、建表脚本、一次性脚本等，单测成本明显高于收益
- `plan.md` / 当前布置里写明**为什么不测**
- 有书面手工验收：打开哪页 / 跑哪条命令 / 看到什么

「这个不好测」一句话不能当例外。

## 用户已经先写了实现

不强迫删光重来。当前小步改成：

1. 补一个**本应失败**的测试（测的是刚才那份实现声称的行为）
2. 先让用户看到：如果把实现挪走或改错，测试会红（能演示就演示；做不到就讲清楚风险）
3. 再把实现对回测试到绿

并告诉用户：先写实现再补测试，测试很容易变成「跟着代码说话」，漏掉真正的期望。

## 布置时你该写清

- 测试文件路径、测试名字、断言的行为
- 精确命令（例如 `mvn -pl backend test -Dtest=XxxTest#method`）
- 红时预期看到什么，绿时预期看到什么

不要给整份可粘贴的生产实现。用户卡住需要示意时，只给数行不完整片段。

## 禁止

- 没看红就写实现（除非走「已先写实现」适配）
- 用 mock 把测试变成测假对象而不是行为
- 一个测试名字里有多个「并且」
- 把配置改动假装成已经单测过
